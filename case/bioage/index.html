BioAge — guessing biological age from a photo

An AI-powered biological age scanner for web and mobile. Users scan their face and body, a vision model estimates their biological age, and a credit-based premium tier unlocks a more detailed result. Available in several languages.

RoleBuilt solo, from backend to release
StackNode.js · Flutter · TypeScript
StatusLive at bioage.login.ac.pk
Node.jsFlutterTypeScriptAI Vision Credit systemMulti-language

Two problems that shaped the product

From the outside the product looks simple: upload a photo, get a number. What makes it hard is exactly the two things the user never sees.

1. The vision model has to face real-world photos

A model that behaves neatly on a test dataset will meet a much messier reality: dim rooms, backlighting, cropped faces, glasses, masks, tilted shots, cheap noisy front cameras, or someone photographing a screen showing another person's photo.

Why this is hard Failure on a product like this can't be an error. A user who sends a dark photo isn't making a mistake — they're just in a dark room. The system has to tell "I can't assess this photo" apart from "I assessed it but confidence is low", and say so in a way that doesn't make anyone feel blamed. Plus one thing that's rarely discussed: the output is a number about someone's body. People react to it emotionally, so calibration and how the result is worded matter as much as the model's accuracy.
The cost that stays attached Inference has a real cost per request. That means every photo processed is money going out, while not every user pays — which ties the model problem straight to the credit-tier design below.
How this was handled Rather than a gate that judges photo quality, the design leans on confidence and on never charging for nothing. Credits are reserved before the vision call and refunded whenever nothing usable comes back — the model errors out, or it returns output that can’t be parsed into a valid result. A genuinely poor photo that still parses isn’t hard-rejected with a “no face / too dark” verdict; it is answered with a low-confidence estimate, and the biological age is returned as a single number carried alongside that confidence (with a body-fat range on body scans) rather than a bare number with no context. The honest seam: there is no server-side face-detection or brightness check — the model is asked to lower its confidence on a weak photo, not to refuse it. The guarantee is narrower than the ideal above: the user is never charged for a result that never arrives, but a weak photo still gets an answer, softened by its confidence rather than blocked outright.

2. One backend, two clients that don't move together

The web is written in TypeScript, the mobile app in Flutter, and both talk to the same Node API.

Why this is hard The web can be deployed today and everyone is on the new version at once. Mobile isn't: the old version stays installed on people's phones for months, and there's no way to force them to update. Which means the API can never really change — it can only grow. Every change to the response shape has to stay safe for a client released a year ago, or you break users who did nothing wrong.
What makes it worse Two clients means two type definitions that can drift apart silently: TypeScript on one side, Dart on the other, and no compiler checking both at once against the API in the middle. This kind of bug doesn't show up at build time — it shows up on the user's phone.
How this was handled The rule was made structural instead of relying on discipline: the schema is only ever allowed to grow. Every migration is a guarded ALTER TABLE ... ADD COLUMN that first checks whether the column already exists — never a rename, never a DROP — so a phone still running last year's build keeps seeing every field it was written against, and simply ignores the ones added since. The second half, two type definitions drifting apart, is answered by refusing to let there be two: the response shape lives in one shared contract that both the TypeScript web client and the Dart app treat as the single source of truth, with the backend clamping and repairing every payload to match it before it leaves the server. The cost is accepted: the database only accretes, columns that outlived their purpose stay as dead weight rather than being cleaned up, because a tidy schema is worth far less than a user on an old app who never notices anything changed.

The constraints that shaped it

  • Pay per inference. An AI model isn't a fixed cost. Every scan adds to the bill, so the credit tier isn't just a way to monetise — it's a cost brake.
  • Mobile can't be forced to update. Backward compatibility isn't a choice, it's a requirement.
  • Multi-language from day one. Not just translating buttons: the scan result is also text that has to read naturally in every language.
  • A face photo is personal data. What is stored, for how long, and why — questions that have to be answered before the first line is written, not after.
