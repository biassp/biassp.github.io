Radar Duit — logging your spending without being asked

An automatic finance tracker. Instead of asking users to type in every transaction, the app reads the notifications banks and e-wallets already push to the phone, parses them, and alerts you the instant money moves. Available as both an Android and a web app.

Why the approach is different

Almost every finance app loses to the same thing: typing everything in by hand is exhausting, and people quit after two weeks. Radar Duit sidesteps that by never asking the user to record anything — its data source is the notifications that land on the phone anyway. That single decision moves all the difficulty somewhere else, and that somewhere is where this project actually lives.

1. Staying alive in the Android background

Capturing notifications needs a NotificationListenerService — a service that has to stay running, with a special permission that can't be requested through an ordinary dialog and forces the user to walk into system settings themselves.

Why this is hard Android is built to kill background processes, and phone makers make it far more aggressive still. Xiaomi, Oppo, Vivo and Realme each run their own battery-management layer that shuts services down without telling anyone — the app included. The danger isn't that the app stops; it's that it stops silently: the user assumes every transaction is being recorded when nothing has been recorded for three days. A finance tracker with silent gaps is worse than no tracker at all.
What it means for the design An app like this can't just work — it has to be able to prove it's still working, and tell the user the moment its permission is revoked or its service is killed by the system.
How this was handled The app re-checks the NotificationListener permission whenever the onboarding and health screens resume, and warns the user if access has been revoked or if battery optimization is throttling the service — because the system can cut it off with no notice. The honest caveat: detecting an unusual silence in incoming notifications and proactively telling the user “nothing has come through in a while” is a planned guardrail, not yet built. So today the guarantee is narrower than the ideal above — the app can prove its permission is intact, but not yet that the stream itself is still flowing.

2. Bank notification formats that never hold still

Every bank and e-wallet writes its notifications differently, and not one of them treats that text as a public interface.

Why this is hard There's no spec, no versioning, no warning when it changes. One bank uses Rp1.250.000,00, another IDR 1,250,000, another abbreviates the merchant until it's unreadable. The direction of a transaction is sometimes "debit", sometimes "dr", sometimes only implied by the sentence. And any of it can change next week when the bank updates its app — without telling anyone. Which means the parser is never finished; it has to be built to fail politely, to flag that a notification wasn't recognised rather than quietly record the wrong amount.
The most expensive mistake Misreading a number is more dangerous than failing to read one. A failure is visible; a misread lands in someone's financial records and gets trusted.
How this was handled Every parse carries a confidence score, and nothing reaches the ledger on the strength of a guess: a per-type gate holds back anything below its threshold — expenses judged more strictly than money-in — so an unrecognised or half-read notification is parked for review rather than recorded with an invented number. The parser is also told to abstain — to mark a notification as not a transaction whenever it isn't clearly one — so the failure mode is a visible gap, never a silent wrong figure. And because a bank's wording drifts without warning, the categories a user corrects are captured in a corrections override table that teaches each fix back into future parsing, promoting a correction to everyone once enough people independently agree on the same one. Erring toward silence has a cost: some genuine transactions wait in an inbox for a tap of confirmation instead of appearing on their own. That is the deliberate side to land on — a line the user can add back is recoverable; a wrong number they already trusted is not.

3. Asking permission to read bank notifications

To work, the app asks for access to one of the most sensitive data streams on someone's phone.

Why this is hard This isn't a technical problem, it's an architectural one. The question is simple and unavoidable: what leaves the phone, and what doesn't? Every byte sent to a server is something that has to be protected, has to be explained, and one day has to be accounted for. The answer that's easiest to build — send everything, process it on the server — is also the hardest to defend when someone asks. And people will ask, because the permission request itself has already put them on guard.
How this was handled On the phone, a package whitelist decides which apps may be read at all — anything outside it (chats, email, social) is never touched. But there is no on-device parser: the full text of every matched notification is batched and sent to the server, where a per-user cache, a DeepSeek AI parser and a merchant-override table turn it into a transaction. Parsing lives on the server, and that is the honest trade-off: the notification text of a user’s financial apps does leave the phone. The upside is that when a bank changes its format the fix ships instantly, with no app update to wait for — so the discipline sits on the other side: keep what leaves as narrow as possible in scope and retention, and say so plainly rather than claim nothing leaves at all.

The constraints that shaped it

  • The data source belongs to someone else. Notification formats can change at any time without warning, so the system has to age gracefully rather than break all at once.
  • Silence is the worst failure mode. Users only trust an automatic tracker if they know when it has stopped tracking.
  • Android is not a friendly environment. This app fights an operating system whose very job is to shut things like it down.
  • Trust comes first. The decision about what gets sent to the server is made before features, not after.
