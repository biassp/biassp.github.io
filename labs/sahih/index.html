Every key, subject and issuer on this page is fabricated, and the issuer enforces it rather than promising it: SAHIH_JOSE.issue refuses to sign a payload whose iss does not end in .invalid — RFC 2606's reserved top-level domain, so the issuer this page names is structurally incapable of existing — or whose sub does not begin u_FIKTIF_. Try it on the Terbit tab and read the refusal.

This page ships no third-party code at all.

Rombak, the lab next door, opens by admitting it ships 878 KB of somebody else's SQLite and that the admission made a claim on this site's own index false. This is the clean case. Real RSA-2048, real P-256 ECDSA, real HMAC-SHA-256, real key import and export — under the same Content Security Policy the six strictest labs ship, byte for byte, with no 'wasm-unsafe-eval', no vendor/ directory, nothing to regenerate and nothing under a foreign licence. One command checks it: diff <(sed -n 13p labs/harvest/index.html) <(sed -n 13p labs/sahih/index.html). The site's dependency count goes from seven of eight to eight of nine, and this is the one place on this site where adding a lab improves a ratio.

The demonstrations are built in your browser, by this page's own JavaScript. While this line is here they have not finished loading — and if it stays, scripting is off, and the sections below the tab strip are the whole of what this page can show you.

What this page does not prove

Every limit below is a real one, and none of them is a limit this page could design away.

There is no server, so there is no trust boundary. The issuer, the verifier and the attacker are three JavaScript objects in one tab with no isolation between them. Every sentence here about what a server can see is a modelling choice, not a measurement.

Authorization is the bigger bug class and it is not here at all. This page is about authentication — establishing who. Broken object-level authorization, the handler that checks the token and never checks whether this actor owns this object, breaks more products than every forgery on this page combined, and it is not modelled. The title says tokens for that reason.

No network, and therefore no cookies. HttpOnly, Secure, SameSite, cookie prefixes, CSRF, CORS, TLS, HSTS, pinning. A page cannot set an HttpOnly cookie from JavaScript by definition — the write silently does nothing and does not even throw — so the single most important session-storage control on the web is structurally undemonstrable here. HARvest audits cookie flags from a real capture; that is where to look.

No second origin, so no OAuth 2.0, no PKCE, no OIDC, no SAML, no SSO. Every property worth demonstrating in those is a redirect between origins.

No sessions. No fixation, no rotation, no idle-versus-absolute expiry, no refresh-token family with reuse detection, no distributed sign-out. The revocation panel on the Claims tab is one Map in one process, with no replication lag and no cache. The hard version — a denylist read by twelve API instances behind a load balancer with a thirty-second cache TTL — is where revocation actually fails, and it needs the thing this page does not have.

No password storage. No Argon2id, no scrypt, no bcrypt: crypto.subtle has none of them. Measured on this page, and printed on the Verify tab as observed data — importKey(..., 'Argon2id', ...) answers NotSupportedError, and so do scrypt, bcrypt, BLAKE2b, SHA3-256 and MD5. Argon2 is defined over BLAKE2b, so building it here means hand-writing a hash function, which is the last thing a security lab should model approvingly. PBKDF2 is what the browser has, not what you would choose server-side in 2026 — the difference is memory-hardness, and PBKDF2-SHA256 has the worst defender-to-attacker cost asymmetry of the modern key-derivation functions because SHA-256 is cheap on a GPU. OWASP's current figure for PBKDF2-SHA256 is 600,000 iterations; it was 310,000 before that and it will move again, which is why a hardcoded recommendation rots into a wrong claim. This page runs no PBKDF2 at all, has no cost curve, and ships no cracker. The one place a password touches a token here is an HS256 secret, and every HS256 secret on this page is 256 bits from crypto.getRandomValues.

No WebAuthn. window.PublicKeyCredential exists in this browser and there is nothing behind it. The only WebAuthn call this page makes is isUserVerifyingPlatformAuthenticatorAvailable(), which returns false, and its result is printed as observed data and is not in the assertion count. How long it takes is not stated here: measured on this machine the same call ran between 0.1 ms and 51.8 ms across eighteen samples, so any single figure in a paragraph would be a number chosen rather than measured. The Verify tab prints the one your browser produced. Registration is not attempted: this repository's test harness serves from 127.0.0.1, an IP literal is not a registrable domain and cannot be a Relying Party ID, and a virtual authenticator over CDP does not fix that. localhost would work and I chose not to change the harness for one assertion. That is a scope decision, not a law of the platform, and stating it the other way round would be the kind of confident wrongness this page exists to avoid.

No timing attack, and this page will not fake one. Measured in your browser when this tab rendered, and printed on the Verify tab: the number of samples, the number of distinct values, the smallest non-zero step, and how many iterations a busy loop runs before the clock moves. Those are your numbers, not mine, and they will differ from the ones in the README. A better clock needs crossOriginIsolated, which needs COOP and COEP response headers, and GitHub Pages cannot set response headers — so this page can never have one, no matter what it does. A real measurement takes roughly a thousand batched repetitions per sample and a rank test that handles heavy ties, and that is stated here rather than run.

Nothing here is a constant-time comparison. crypto.subtle.verify performs the signature comparison and this page cannot inspect it. There is no crypto.subtle.timingSafeEqual — it is absent from SubtleCrypto.prototype, which this page prints — and there is no shipped proposal for one. A hand-written XOR-accumulate loop is a good habit and a bad claim: the engine tiers it, deoptimises it, bounds-checks it, and the garbage collector can pause anywhere inside it.

No revocation infrastructure, no key rotation, no JWKS. A jku header is refused by name here, and the reason is structural rather than principled: connect-src 'none' means this page could not fetch a key set if it wanted to. On a real server that refusal is a decision somebody has to remember to make.

A bearer token is a bearer token, and the fix is not on this page. The last card proves that a signature is not an identity. The 2026 answer to that class is a sender-constrained token — DPoP (RFC 9449, 2023) or mutual-TLS-bound (RFC 8705, 2020) — which binds the token to a key the holder must prove possession of on every request. Neither is demonstrable here: both need a server and a second party.

No memory hygiene, no side-channel resistance, no audit. JavaScript cannot zero a key; there is no mlock; the garbage collector copies strings freely. Nobody has reviewed this code. The suite tests properties I chose, which is the weakest form of assurance there is, and nothing here is a security review of anything.

What this is for. HARvest ships a JWT decoder carrying the comment "This NEVER verifies the signature: verification needs the signing key, which this page does not have and will not ask for." That is the correct posture for a page holding a stranger's capture, and it leaves half a sentence open. This page closes it, because it made the keys milliseconds ago in your own tab. That is the whole claim. This is a statement about what a browser can and cannot show about token verification — not a maturity claim about any system I ship, and no product of mine is named or modelled anywhere on this page or in its README.

The claims this page refuses to make

  • never "this is secure", "unhackable", "bank-level", "military-grade";
  • never "constant-time comparison";
  • never "timing attack demonstrated";
  • never "PBKDF2 with N iterations is safe", and never any GPU cracking rate as measured — a browser cannot produce one, so this page states none;
  • never "salts are secret";
  • never "TOTP is two-factor" without adding that a shared secret in the same password manager is one factor with extra steps, that the server can generate your codes, and that it is phishable in real time;
  • never "verified the JWT" without naming the key: it verified this token against a key this page generated, and it will not ask you for one from anywhere else;
  • never "zero dependencies means secure" — it means one thing, that there is no third-party code in this lab's supply chain, and says nothing about the correctness of the code that is here;
  • never "every lab on this site ships connect-src 'none'" — labs/saku/index.html ships connect-src 'self' and is a PWA share-target demo;
  • never "the whole attack surface of a bearer token" — this page covers the attack surface of token verification, which is a much smaller thing, and the list above says what the rest of it is.

Why this page shows attacks at all. Every forgery here exists to show the line that stops it. The naive verifier is not a straw man — it refuses five bad tokens on the first card, before it is shown taking the sixth — and the strict verifier's refusal is the last thing on every panel. The tokens are this page's own, minted milliseconds ago — the HMAC key from crypto.subtle.generateKey in your tab, the RSA and ECDSA keys imported from the published RFC 7515 A.2 and A.3 test vectors, each labelled with its provenance on the Terbit tab — and there is nowhere to paste one in from anywhere else. The page cannot reach the network: connect-src 'none' is a browser refusal, not a promise, and the counter in the header reads whatever the browser actually let through.

The signature is the easy part. That is the one sentence this page exists to make runnable. Three of the five rungs above are stopped by a single line at the verifier, two of them by the same line. The fourth is not a forgery at all — those tokens are correctly signed, and refusing them takes six separate claim rules. The fifth is not a forgery either, and nothing a verifier can do stops it: it is stopped by a decision made somewhere else entirely.
