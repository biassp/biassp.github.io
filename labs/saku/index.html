The share handler, provable on this device

Saku declares share_target with method: POST. On Android, picking Saku from the OS share sheet makes the operating system send a real multipart/form-data POST at ./share — with the app closed and the network off. GitHub Pages would answer that POST with 405. It never gets there: the service worker controlling this scope intercepts it, parses the FormData, writes the row to IndexedDB and replies 303 to a GET URL.

That path is Chromium-on-Android-only and needs an install, so the button below fires the same POST at the same endpoint from this page. Same worker, same FormData parse, same atomic write, same 303 — on your laptop, right now.

      What this proves, and what it does not

      • A service worker answering an OS-generated multipart POST with no server in the path.
      • One IndexedDB transaction spanning entries + outbox + the Lamport counter, aborting rather than half-writing.
      • POST/Redirect/GET inside a worker, so the back button cannot duplicate an entry.
      • Versioned schema migration, quota reporting, backoff with jitter, cross-tab claim leases.
      • Not a backend. The sync peer is an IndexedDB store in this page, labelled as such everywhere it appears.
      • Not Flutter, Dart, a native build or a store release. This is web-platform engineering and is filed as exactly that.
      • Not Web Push. Server push needs a push service and VAPID keys; neither can exist on static hosting, so it is not shipped.
      • "No network" is a claim about this page only. It makes zero requests after load — the CV's own home page does call the GitHub API.
