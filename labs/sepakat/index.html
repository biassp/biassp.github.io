Four technicians, one job board, and no server to referee it

Every phone holds the whole board and edits it offline. When two of them are connected they gossip directly. Nothing is in charge, so there is no lock to take and no moment when a write is the write — which means the interesting question is not whether the phones end up agreeing. It is what they agree on, and whose work is missing from it.

Three merge strategies run below against the same user actions, the same latencies, the same duplicate deliveries and the same partition. The one that loses data is not the one that looks broken: it converges quickly, quietly, and on a number nobody typed.

Every technician, job and timestamp on this page is generated from a seeded pseudo-random number generator in net.js. None of it is real, and none of it leaves the tab.

The one field where a register is not good enough

A job title is a single value, so a register handles it: one of the two edits wins, deterministically. A report is not — two technicians adding a line each should end up with both lines. The properties, run in this tab

Merge laws over random states, convergence over random schedules, and the quantities each engine is supposed to preserve or destroy. Roughly a quarter of them pass only when something refuses, loses or diverges — a foil that quietly started working would turn this red, and it is meant to.

The three strategies

Op log, applied on arrival. Send what the user did; do it again on the other side. Every line of it is reasonable, and it fails on the two things a real network does constantly: a message delivered twice happens twice, and two messages that arrive in a different order at different phones leave those phones in different states — permanently, with nothing to bring them back.

Last writer wins. Send state, keep the value with the higher timestamp. This genuinely converges: it is a real join, and duplicates and reordering are both harmless to it. What it cannot do is represent two writes. A concurrent edit is resolved by discarding one of them, silently, and which one survives is decided by whose phone clock was fast. +3 and +2 over a 5 becomes an 8 or a 7 — never a 10.

CRDT join. Pick a type per field whose merge is commutative, associative and idempotent, so any order of any deliveries lands in the same place. What exists is an OR-Set; the numbers are a PN-Counter, which adds up per replica so nothing is ever overwritten; single-value fields are still registers, but stamped with a hybrid logical clock so that a reply can never be ordered before the message it answers, whatever the clocks say.

Where the CRDT column is also lossy, and why that is fine

The job title in the crdt column is a register too. Two people renaming a job concurrently still ends with one title. What changed is the reason: the winner is decided by causality rather than by clock skew, and the outcome is the same on every phone and in every replay.

For a field where both edits genuinely have to survive, a register is the wrong type and no amount of better stamping fixes that — you need a sequence. That is the Text merge tab: the same two edits, once through an RGA and once through a register, side by side. A board field is not text just because it holds a string, and pretending otherwise is how a "CRDT sync" ends up losing exactly as much as the thing it replaced.

What the network is allowed to do

  • Reorder freely. Latency is drawn per message per link, so later messages routinely overtake earlier ones.
  • Deliver twice. At-least-once, decided per link — one phone can see a message twice while its neighbour sees it once.
  • Hold traffic. A partition defers everything crossing it until the link returns.
  • Disagree about the time. Each device carries a fixed skew, one of them by seconds.
  • Never lose a message for good. This is the one thing it may not do — and it is a restriction on the simulator, not a favour to the engines. If messages could vanish, a divergence could always be blamed on the network instead of on the merge.

What this does not model

  • Byzantine peers. Every replica here is honest and correct; a phone that lies about its own state is a different problem with different answers.
  • Tombstone growth. OR-Set tags and RGA nodes are kept forever. A real deployment needs a compaction story, and this page does not have one.
  • Authentication and access control. Anything a peer says is accepted.
  • Bandwidth. Deltas here are small because the board is small. State-based CRDTs get expensive in ways a four-job demo will never show you.

Reading the numbers

Agreement is whether every phone's board serialises identically. Totals compares the point column against the sum of every increment the script contained — a number that is knowable regardless of interleaving, because addition does not care about order. That second check is the one that catches the failure people miss: an engine can be perfectly converged and still be wrong, and only the totals column can tell you.

How the no-server claim is enforced. This page ships connect-src 'none' in a <meta http-equiv="Content-Security-Policy"> tag in its own source, so the browser refuses every outbound connection whatever the JavaScript asks for. The counter in the header wraps fetch, XMLHttpRequest, WebSocket and sendBeacon and shows how many were attempted. Open DevTools and watch the Network tab stay empty: the four "phones" are four objects in one tab.
