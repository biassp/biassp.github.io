Serobot

The same money twice — once as a stored column, once as an append-only ledger — with two writers on both. Nothing leaves this tab.

network calls from this page: 0 CV

This page vendors nothing and relaxes nothing.

No framework, no bundler, no build step, no vendor/ directory and nothing under a foreign licence. Real dedicated Web Workers, a real IndexedDB database created and destroyed by each run, and a real navigator.locks queue — under the same Content-Security-Policy the seven strictest labs on this site ship, byte for byte, with no 'wasm-unsafe-eval' and no widened connect-src. One command checks it, and it prints nothing when it passes: diff <(sed -n 13p labs/harvest/index.html) <(sed -n 13p labs/serobot/index.html). worker-src 'self' blob: was already in that line before this lab existed, so spawning workers cost the policy nothing.

What that policy does not do is reach a worker, and that is measured rather than assumed — it is the first item under What is still not covered, below, and the reason every worker on this page loads the same guard.js the header badge reads.

This machine, read at load

Every value in this block is read from your browser's runtime as this tab renders. None of it is typed into this file, and none of it is asserted by the suite — a machine description is an observation, and pinning one is how a suite goes red on somebody else's laptop.

The capability probe runs in your browser, from this page's own JavaScript. While this line is here it has not finished loading — and if it stays, scripting is off, and the prose below the tab strip is the whole of what this page can show you.

Every figure on this page was produced by your browser just now. Two badges tell you which kind each one is: asserted means the suite pins it and CI would go red if it moved; measured means it is a real number from a real run and no assertion touches it, because it is a race outcome or a stopwatch reading and pinning either is how a suite goes red on somebody else's laptop.

Before anything else, what this browser will not do. crossOriginIsolated is false and SharedArrayBuffer is undefined — printed above, live, not transcribed. GitHub Pages cannot send the COOP and COEP headers that shared memory requires, and it never will; that is a static-host limitation, permanent, and not a setting this repository can change. So there is no spinlock here, no futex, no seqlock, no ring buffer, no memory model, no fences, no false sharing, and nothing on this page is a simulation of one over postMessage wearing its name. The obvious primitive is unavailable, and every mutual-exclusion mechanism on this page exists because of that. That is the constraint, not an apology for it.

One correction to the easy version of that paragraph, because a reader with a console will check. Atomics is not inert. On a plain Int32Array, Atomics.add returned 0, Atomics.load 5, Atomics.compareExchange 5, Atomics.store 3, Atomics.exchange 3, Atomics.notify 0, and Atomics.isLockFree(4) true. Only wait and waitAsync throw TypeError. How many members were probed, how many returned a value, and how many function members this browser's Atomics carries at all are three counts derived at runtime and printed on the Limits tab — deliberately not written into this paragraph, because the last of them changes the day Chromium ships a new member and a sentence here would go stale with nothing able to see it. What Atomics gives you here is a genuine compare-and-swap over memory no other thread can reach, which is x++ with ceremony.

Not built, stated plainly

Concurrency in a browser is mostly things you cannot do, so this list is longer than the list of what is real. That asymmetry is the honest shape of the subject.

  1. No shared memory, and therefore none of the textbook primitives. Above, in its own paragraph, because it is the constraint the whole page is built inside.
  2. No network, and therefore not the hard problem. No partition, no packet loss, no reordering, no retry storm, no at-least-once delivery, no backpressure, no load shedding. The genuinely hard question — did it fail, or is it just slow? — cannot even be posed here, because there is no remote party whose silence is ambiguous. That is the difference between a concurrency lab and the other kind, and conflating the two is the field's most common tell.
  3. No durability and no crash. Nothing is killed mid-write, no tab is force-closed, no disk is pulled. Nothing here asserts what IndexedDB leaves behind after an abnormal termination. This is also why the split-transaction idempotency panel shows a seam rather than a lost credit: the failure it warns about needs a process to die, and this lab cannot kill one.
  4. No second clock. One wall clock for every worker on this page, so there is no skew to demonstrate and nothing here is ordered by time. One clock trap does exist and is named: performance.now() has a different time origin in a worker than on the page — measured 49 ms apart in one run. performance.timeOrigin is exposed in both scopes so the two are reconcilable, but they are not directly comparable, and this page never compares them. Every ordering claim on this page runs on integer sequence numbers, and a guard refuses a timestamp handed in as an ordering key.
  5. No consensus, replication or leader election. The lease in labs/gudang/ is not leader election: there is no failure detector, only a wall-clock TTL.
  6. Nothing SQL-shaped. No isolation levels, no MVCC, no snapshot isolation, no SELECT … FOR UPDATE, no advisory locks, no BEGIN IMMEDIATE, no WAL, no busy_timeout, no deadlock victim selection.
  7. No online migration. Rombak's hardest admitted item is not closed here either.
  8. No IndexedDB starvation demo, because there is none to build. Measured while this lab was built, and re-derived independently afterwards in a second harness that shares no code with it — not re-run on your visit, so this one is transcribed and says so. A readwrite transaction opened behind three self-perpetuating readonly chains — chains that kept creating new transactions after the writer was created — waited between 1 and 5 ms, with anywhere from three hundred to six thousand readonly transactions already completed depending on how long the chains had been running and how hard the CPU was throttled. IndexedDB starts overlapping-scope transactions in creation order, so a transaction only ever waits on transactions created before it. The specification forbids the starvation and this build honours it. The page says that rather than staging one.
  9. No IndexedDB transaction-timeout demo, because there is no timeout. Measured while this lab was built and not re-run on your visit: a transaction held busy for two and a half seconds ran several thousand read-modify-writes and committed cleanly, with onabort never firing and tx.error null. The exact count moved between eight and ten thousand across machines and is not a figure this page claims — see the throughput item below. What did not move is that nothing timed the transaction out.
  10. No cross-origin anything. Web Locks, IndexedDB and BroadcastChannel are all origin-scoped. Every mechanism here protects one site from itself.
  11. No scheduler control. You cannot pin a worker to a core, set a priority, force a preemption point, or make an interleaving repeat. Chromium throttles workers and timers in hidden tabs; a background tab produces different results and this page cannot prevent it, which is why visibilityState is printed beside every batch.
  12. No ordering guarantee between a BroadcastChannel message and the IndexedDB commit it announces. A receiver that reads on notification can read stale. The page does not demonstrate it and therefore does not imply the ordering holds.
  13. No fairness claim beyond printing the queue, and no starvation demonstration for the optimistic path. A slow writer can lose a compare-and-set indefinitely; nothing here shows it, and the mandatory retry cap exists precisely because it cannot be ruled out.
  14. No proof of absence. Every green run is one sample of a nondeterministic space. A run in which nothing was lost is not a run in which nothing could be lost.
  15. No cross-tab assertion. test/labs.test.js opens one page and calls page.evaluate once, so nothing cross-tab is assertable here; the storage event never fires in the same document and does not exist in workers at all. The one cross-tab affordance on this page is labelled unasserted.
  16. No throughput claim and no benchmark against anything. hardwareConcurrency is 4 on the machine that runs CI. A browser is not a runtime you benchmark against.
  17. app.js has no automated control. The suite asserts the engines; nothing asserts the renderers. Every number written into page prose is unasserted by construction — a sibling lab found this when a mutation restoring a wrong hardcoded year left all 419 assertions green.
  18. No assertion here is a conformance test of the browser — and the honest version of that sentence is narrower than the one this page used to carry. Nothing here sets out to prove that postMessage delivers or that structuredClone clones; those are Chromium's tests. But the suite does pin the exact strings the browser produced and this page prints — the lock ordering a-in,a-out,b-in,b-out, the shared-then-exclusive order s1-in,s2-in,x1-in,s3-in, the two keys query() returns and the three in every entry, what each Atomics member returned, the DOMException names. A printed ordering that nothing checks is prose. The price of pinning them is that they would go red if Chromium changed its behaviour, and this lab pays it knowingly rather than claiming a boundary it does not hold.

The claims this page refuses to make

  • Not "there is no concurrency anywhere in this portfolio." labs/gudang/store.js:135-152 ships a cross-tab TTL write lock whose comment already asserts, in prose, the exact property this lab measures. labs/siakad/solver.worker.js and labs/rombak/tests.worker.js are real workers. PROGRESS.md records a shipped concurrency bug — ledger ids from a per-tab counter used as an IndexedDB key, one tab silently destroying another's entries, fixed by put() → add() — and gudang's own admitted residual sub-second race on a lapsed 9-second lease. Concurrency has appeared here three times — once as a bug, once as a mitigation, once as an admitted gap — and never as the subject. Gudang's lock comment is a load-bearing claim that has never been measured. This page measures it, and it is correct.
  • Not "this closes the gap rombak declared." Rombak's "Not built" names five things: BEGIN IMMEDIATE, WAL mode, busy timeouts, lock contention, and a migration running while writes arrive. This lab closes two — lock contention and concurrent writers — in a different storage engine, and leaves the three SQLite-specific ones and the hard one, online migration, exactly where they were. A reader who follows the link and re-reads that sentence should find the arithmetic already done for them.
  • Not "real OS-thread parallelism caused the lost update." The cause is a read-set that spans a transaction boundary. The identical loss happens on one thread with nothing running in parallel at all — that is the panel one tab over, and it is exact where this one is not. Parallelism makes the interleaving easy to hit; it is not what makes it possible.
  • Not "IndexedDB is ACID", and no isolation level is named. The defensible claim is narrow and is the one made: the specification requires read-write transactions with overlapping scope to start in creation order and not run concurrently, so a read-modify-write contained in one transaction cannot interleave with another — and that is what was measured.
  • Not "navigator.locks gives you mutual exclusion." It serialises the callers who ask. It is advisory: code that never requests the lock walks straight past it, and a name cannot be made mandatory. It is origin- and agent-scoped. What it gives you that a TTL lease does not is release-on-death — so no expiry window for a dead agent. But a frozen-but-alive agent holds a Web Lock indefinitely with no timeout of any kind, where a lease at least lapses; and steal: true, demonstrated here, constructs exactly the two-parties-both-believe situation that fencing tokens exist for. It is a trade with two columns, not a fix.
  • Not "we proved the safe path is safe." It lost nothing in the runs on this machine. That is evidence, not proof: a race that does not fire is indistinguishable from a race that cannot. The reason to believe the single-transaction path is safe is the specification; the runs are a check that this browser implements it.
  • Not "we fixed the race." This shape of race is not reachable through this code path. Other shapes are not addressed and are not claimed.
  • Not "zero network calls, so nothing left the tab." connect-src 'none' is a browser refusal, not a promise, and the counter above measures attempts, not outcomes — under that CSP navigator.sendBeacon still returns true.
  • Not one word of distributed, consensus, quorum, CAP, Raft, Paxos, two-phase commit, split brain, replication, eventual consistency, leader election, linearizable, lock-free, wait-free, ACID, or any SQL isolation level — except in the list above, as things this lab does not do.

What is still not covered

  • The network counter in this repository's lab headers only ever watched the main thread. A <meta http-equiv> Content-Security-Policy applies to the document, not to a dedicated worker's global scope, and GitHub Pages sends no CSP header at all — so a worker has effectively no policy. Measured on this page's own CSP: a fetch from the page was refused and wrote two console errors; the identical fetch from inside a same-origin worker resolved with the body, silently, with nothing logged. window.SEROBOT_GUARD.total() — the exact expression CI evaluates — cannot see it. Every worker here importScripts('guard.js') and posts its own total back to be folded into the page count before anything is reported. Two sibling labs already ship real workers under the same badge while making a weaker claim, and this page says so rather than quietly being the only correct one.
  • No worker or page here ever attempts real egress to prove the counter works. Each refusal the browser issues writes a console error, and CI counts one console error as a broken page. The counter's arithmetic is asserted instead, against a throwaway clone.
  • A finding about this repository's own shipped code, and this lab does not fix it. labs/saku/sync.js:47 peerApplyOne reads through peerGet (a readonly transaction), decides whether the idempotency key was already seen, and writes through peerPut (a later readwrite transaction) — character for character the shape the centrepiece loses updates with. A second, separate finding in the same function: rec.seen is truncated to the last 50 entries, so a key returning after 50 other operations is accepted again — a bounded replay window. drain() applies operations through a strictly sequential reduce, so within one drain these calls never overlap; two overlapping drains would reach it. This lab reproduces the shape and shows what it costs. It does not claim saku loses data today, and no live path that does was found. labs/saku/README.md carries both findings.
  • The firewall's limit, as a number rather than a hedge. Both routes on this page bottom out in the same IDBObjectStore and the same scheduler.
  • app.js has no automated control, above.

The RepBout bridge

A case study on this site lists four paths by which a balance can be created from nothing. The fourth, in its own words, is "two requests arriving at once and both reading the old balance before either one writes." This lab is the fourth one, reproduced in a browser tab, with a fabricated unit and no money in it.

What this lab cannot tell you about a real system: there is no second server here, no database row lock, no SELECT … FOR UPDATE, no unique constraint on a server-side idempotency table, and no transaction manager below the application. Real ledgers are protected below the application. This lab is what the problem looks like when they are not — which is exactly the situation you are in whenever a database is used as a key-value store, and exactly the situation IndexedDB puts you in permanently.

No table names, no endpoints, no key format, no webhook provider, no amounts, no claim that system is free of this bug, and no statement or implication that a real user's balance was ever wrong. And nothing that says its gems balance is derived — that page states plainly that the gems column is still a stored number and that the migration is the intended next step; contradicting a published page one click away, in the exact place it went out of its way to be honest, would cost more than this whole lab gains.

How a nondeterministic result is presented without looking staged

The free-mode panel, in order, top to bottom:

  1. The batch size, printed before the batch starts. There is no retry policy on this page and the suite asserts roundsExecuted === roundsRequested. Nothing loops until it sees a loss.
  2. Every sample, as a strip. 21, 22, 20, 23, 22, 24, 21, 25, 22 — not a summary. That is what a real race looks like and what a fabricated one does not.
  3. Min / median / max, and the count of runs that lost nothing, printed whether it is 0 or the whole batch. Never hidden, never a fallback branch.
  4. The machine beside it — hardwareConcurrency, deviceMemory, visibilityState, the user agent, all read at runtime. A race result without a machine is not a result, and this also pre-empts "it didn't reproduce for me": of course it didn't, and the page said which machine.
  5. "No loss observed on this machine today", in the slot the shortfall would have occupied, if that is what happened. The prose is generated from the batch, so the page cannot claim a shortfall the batch did not find. That behaviour is the difference between a demo and an instrument, and it is the first thing a hostile reader tries.
  6. The control, in the same batch, in the same seconds, with the same parameters. Safe and unsafe alternating, never safe-then-unsafe.
  7. The one-line diff, from the live functions, with the marked line, plus artificialDelayMs: 0 printed per arm and a one-command grep that finds no timer.
  8. The barrier column beside it, where the number does not move — and the sentence that the barrier forces the worst case every time, runs in all four arms, and three of them lose nothing.

Why this page ships a broken path at all. The losing column is the interesting result, so it is never coloured as an alarm: the verdict family here is indigo, amber, sky and grey, because a red-and-green matrix on this page would train a reader backwards inside two cards and no glyph beside it undoes a colour learned that fast. The word and the error code carry the verdict, and every cell stays legible in monochrome.

The barrier is a message count, not a delay. Nothing on a write path waits for a clock: no busy loop, no Atomics.wait — there is no SharedArrayBuffer to wait on — and no call that makes anything happen later, because a delay would make the loss a property of the delay rather than of the code. Two deadlines do exist and are named rather than swept under that sentence: the lock request's AbortSignal.timeout, printed in the arm body itself, and the barrier's per-phase deadline, which is a timer function the worker passes in. Neither fires on a path that succeeds. One command shows where the timers are not: grep -n 'setTimeout\|setInterval' labs/serobot/arms.js prints nothing — which is a fact about that one file, not a proof about the whole path, and the suite is what pins the rest, re-scanning the shipped function bodies at runtime and pinning the exact list of deadlines they arm.
